# OKR Master

## Product Vision

Build a local OKR planning and review application with two roles:

- **Editor:** a local Electron desktop app used by the project owner to plan,
  edit, and review OKRs. It is the only place where data changes.
- **Viewer:** a single self-contained, read-only HTML file generated by the
  editor. The team opens it in a browser, from SharePoint or a local copy, to
  see the current cycle and history without installing anything.

The application should provide a structured process for strategic planning, OKR definition, execution tracking, cycle reviews, historical performance analysis, and continuous improvement.

The application must be simple, fast, transparent, and fully owned by the user.
No hosted services or subscriptions are required. Viewers must not need
Node.js, npm, a terminal, admin rights, or an installation.

The solution should support future expansion while maintaining backwards compatibility with existing project data.

---

# Goals

The product should:

- Support long-term strategic direction through Company Goals.
- Support Objectives and Key Results according to established OKR principles.
- Support execution tracking through Initiatives.
- Enforce a structured planning → execution → review workflow.
- Encourage regular reflection and continuous improvement.
- Keep all project data under the user's direct control.
- Remain simple enough for a single person to use privately.
- Share current OKR status with a team through a read-only viewer under one
  stable link, without hosting a server.
- Allow future expansion without breaking existing projects.

---

# Non-Goals (MVP)

The initial version should NOT include:

- User authentication
- Hosted servers, cloud synchronization, or live data in the viewer
- Multi-user editing, edit locks, or real-time collaboration
- Comments or feedback inside the viewer
- Email notifications
- Mobile applications
- AI-generated objectives or reviews
- Integration with third-party OKR platforms
- Advanced reporting dashboards
- Custom weighting of Key Results
- Complex permissions or role systems

These features may be added in future versions.

# Technical Constraints

## General

The application must:

- Run the editor completely locally as an Electron desktop application.
- Provide a Windows unpacked editor application; it must run without a
  separately installed Node.js/npm. The full application folder is used by the
  project owner only and is not distributed to the team.
- Keep the editor source structured so a macOS package can be built on a Mac
  later; a Mac editor package is not part of the current scope.
- Generate the team viewer as one self-contained HTML file with all scripts
  and styles inlined, no external requests, no server, and no sign-in logic.
- Show the same application version unobtrusively in the editor and viewer.
  Keep one canonical version in package metadata and do not store application
  version information in project data or change the project schema for it.
- Function without internet access, except when publishing through
  OneDrive sync or Git.
- Store data on the local filesystem.
- Keep project data outside the application executable or bundle.
- Share business logic, schemas, and UI components between the editor and the
  viewer.

## Preferred Technology Stack

Desktop shell:

- Electron

Frontend:

- React
- TypeScript
- Vite

Local API and persistence:

- Node.js
- Express
- TypeScript
- JSON project file; no database required for version 1

The packaged application uses Electron's bundled runtime and Chromium-based

Storage:

- No database required for version 1

# Recommended Architecture

Use Electron as a shared desktop shell around the existing React, TypeScript,
Vite, Node.js, and Express application, with separate responsibilities:

- The Electron main process owns the desktop window and application lifecycle,
  starts and stops the local API, and provides operating-system file dialogs.
- The React renderer implements the application views, forms, validation
  feedback, Kanban board, and autosave state. It must not have unrestricted
  Node.js or filesystem access.
- The Express server exposes project operations and owns project-session and
  persistence operations. It must bind only to the loopback interface, use an
  available port, and stop when the desktop app exits.
- Domain services implement cycle transitions, validation, and progress
  calculations independently of the UI and HTTP layer.
- A persistence adapter loads and saves the single project JSON document,
  validates its schema version, and performs explicit migrations.
- Shared TypeScript types and validation schemas define the project and API
  contracts.

The packaged app serves built frontend assets locally and does not open an
external browser. In development, the Vite development server may continue to
serve the renderer. The Express API and project persistence remain available
through the app's local boundary; project paths are selected using native
operating-system dialogs. Isolate file selection behind an adapter so
platform-specific implementations can be tested independently.

Electron security requirements:

- Disable Node.js integration in the renderer and enable context isolation.
- Use a narrowly scoped preload bridge only when required.
- Do not load remote pages or remote code into the application window.
- Restrict navigation and new windows to the local application.
- Do not expose the local API beyond loopback.

Keep source, build configuration, and platform assets in a form that can be
transferred to a Mac. Build the Windows and macOS packages on their respective
operating systems. The Windows executable is not itself the Mac package.

The viewer is built from the same source as a second Vite target. It runs
without the Express API and Electron, renders existing components in a
read-only mode, and receives its data from an embedded snapshot. See "Team
Viewer and Publishing".

# Project Storage

The application manages projects. Each project is stored in one human-readable
`project.json` file selected by the user. Only one project can be loaded at a
time. The file is the authoritative source for all project data; history is
derived from completed cycles rather than duplicated in another file.

The user can create a project file or browse to open an existing one. The
desktop application remembers the last project path in its per-user
application settings and attempts to reopen it at launch. If it has moved,
become unavailable, or cannot be read, the editor remains usable and explains
that the project must be opened manually. This setting is not project data and
does not change the project schema.

Every stored entity must contain a stable UUID. The project file must include a
schema version:

Example:

```json
{
  "schemaVersion": 1
}
```

# Domain Model

## Project

Represents a single OKR workspace.

Fields:

- id
- name
- description
- schemaVersion
- cadence
- currentCycleId
- planningDraft (optional)

`cadence` is the cadence selected for the next cycle to be planned. Each Cycle
stores the cadence selected for that cycle, which determines that cycle's
duration. The first cycle starts in the calendar month in which its planned
OKRs are submitted.

`currentCycleId` is null until the first planned cycle is submitted.

The project name is required. The project description is optional and may be
left blank; any text entered is stored and displayed as project metadata.

---

## User

Represents a person participating in the project.

Fields:

- id
- name
- email
- active

User details associated with a completed cycle must be retained in that cycle's
historical snapshot.

An active user can be assigned to objectives, Key Results, Initiative owners,
or Initiative collaborators in a planned or active cycle. Deletion is blocked
while any such assignment exists. The user must first be removed or replaced
in every planned or active assignment. Deleting a user must not alter completed
cycle snapshots.

---

## Company Goal

Represents a long-term strategic goal.

Rules:

- A planning phase defines the Company Goals for the cycle it is preparing.
- Maximum 3 Company Goals may be defined for a cycle.
- Company Goals have a priority order, with priority 1 representing the most
  important goal. They do not form a parent-child hierarchy.
- Priorities are consecutive integers starting at 1 (highest) and ending at
  the number of goals, up to 3.
- Objectives must be connected to at least one Company Goal from their cycle.
- Editing Company Goals during planning changes the goals for the upcoming
  cycle only; completed cycles retain their original Company Goal data.

Fields:

- id
- cycleId
- title
- description
- priority

---

## Cycle

Represents an OKR period.

Examples:

- Quarterly
- Monthly
- Yearly

Fields:

- id
- startMonth (year and month, e.g. 2026-10)
- endMonth (year and month, e.g. 2026-12)
- status
- cadence
- planningFocus
- companyGoalSnapshots (created on review submission)
- userSnapshots (user IDs, names, and emails for users referenced by the cycle)

Status values:

- planning
- active
- completed

Rules:

- Only one cycle can be active at a time.
- Cycle boundaries use whole calendar months only; day-level dates are not
  stored or used.
- The first cycle starts in the calendar month when its planned OKRs are
  submitted.
- Cadence determines the cycle's length: monthly is one month, quarterly is
  three months, and yearly is twelve months.
- The cycle period includes every calendar month from `startMonth` through
  `endMonth`, inclusive. No day-level cycle dates are stored.
- `endMonth` is calculated by adding the cycle's cadence duration in months
  and subtracting one month. For example, a quarterly cycle starting in
  2026-10 ends in 2026-12.
- Each cycle's cadence is selected during that cycle's planning phase and
  determines that cycle's end month. Changing cadence for a later cycle does
  not change the duration or end month of a preceding cycle.
- New planning drafts default to quarterly cadence. Monthly and yearly remain
  available, and opening an existing planning draft preserves its saved
  cadence.
- A subsequent cycle starts in the month immediately after the preceding
  cycle's end month, so cycles are consecutive and non-overlapping.
- A review may be prepared and submitted for the active cycle at any time.
  Until submission, the cycle remains active and editable. Submitting the
  review completes and locks the cycle, and unlocks planning for the next cycle.
- The first cycle does not require a review before its activation.
- At most one cycle may be in planning status at a time. The planned cycle and
  its OKRs are saved as a draft until explicit submission changes its status
  to active.
- Each planned cycle must contain at least one Company Goal, one Objective,
  and one Key Result before activation. Each Objective must have at least one
  Key Result.
- Initiatives are optional at activation and may be added or edited throughout
  the active cycle.
- Cycle data becomes immutable when its review is submitted. Historical data
  must retain the Company Goals and user details assigned to that cycle, even
  if those records are later changed or removed elsewhere. Deleting or changing
  a project-level record must not cascade into completed-cycle data.

---

## Objective

Represents an outcome to achieve.

Fields:

- id
- title
- description
- ownerId
- companyGoalIds
- cycleId

Rules:

- Exactly one owner.
- Must belong to exactly one cycle.
- Must belong to at least one Company Goal assigned to that cycle.
- Must have at least one Key Result before the Objective can be saved.

---

## Key Result

Represents a measurable outcome.

Fields:

- id
- objectiveId
- title
- description (optional)
- ownerId
- metricType
- startValue
- currentValue
- targetValue
- progress (derived)

Rules:

- Exactly one owner.
- Must belong to one objective.
- Description is optional and may be left blank; use it for measurement
  context only when the title and metric do not make the source or scope clear.

Supported metric types:

- Number Target
- Percentage Target
- Yes / No

Number Target and Percentage Target require numeric start, current, and target
values. Start and current default to 0; target is required. A target of 0 or a
target equal to the start value is invalid.

Yes / No uses a dropdown with the choices No and Yes. The starting value is
fixed to No and the target value is fixed to Yes; neither is editable. The
user selects the current value, which defaults to No. Progress is derived from
the current value and is not independently edited or stored.

---

## Initiative

Represents work performed to influence a Key Result.

Fields:

- id
- keyResultId
- title
- description (optional)
- ownerId
- collaboratorIds
- priority
- targetDate
- status
- progress
- tasks (ordered list of Initiative Tasks)
- syncProgressToTasks (defaults to false)

Rules:

- Exactly one owner.
- Zero or more collaborators.
- Must belong to one Key Result.
- The Initiative description is optional and may be left blank.
- Tasks have stable UUIDs, task text, and a completed state. An Initiative
  editor starts with one blank task row; blank rows are not stored as tasks.
  Tasks can be added, edited, deleted, and reordered. Completed task text is
  displayed in gray.
- By default, task changes do not affect Initiative progress or status. An
  empty task list has no effect. Moving an Initiative to Done is blocked while
  any defined task remains open.
- When progress synchronization is enabled, progress is the rounded percentage
  of defined tasks completed. Completing all tasks sets progress to 100% and
  status to Done. Reopening a completed task recalculates progress and returns
  the Initiative to In Progress. Enabling or disabling synchronization with
  defined tasks requires confirmation.
- Progress is an integer percentage from 0 to 100.
- Setting status to done sets progress to 100%.
- Setting progress to 100% automatically sets status to done.
- Entering a progress value for an Initiative in To Do moves it to In Progress
  immediately. Moving it from To Do to In Progress through the status control
  requires the user to enter a progress value rather than reusing the existing
  value.
- A Blocked Initiative may have any progress value below 100%; progress of
  100% always sets the status to Done.
- Changing status from done to another status requires the user to enter a new
  progress value below 100%.
- A Done Initiative cannot be saved with progress below 100%; select another
  status before saving a lower progress value.

Priorities:

- 1 (Highest)
- 2
- 3 (Lowest)

Status values:

- todo
- in_progress
- blocked
- done

---

## Review

Represents the retrospective of a completed cycle.

Fields:

- id
- cycleId
- successes
- failures
- lessonsLearned
- nextActions
- overallProgress
- completed

All four review responses (successes, failures, lessons learned/improvements,
and next actions) are required and must contain at least one character.
The review form displays each review question without a separate category
label.

`overallProgress` is the rounded arithmetic mean of the completed cycle's
Objective progress values.

On completion, the cycle must retain the Company Goals and the display details
of its assigned users as an immutable historical snapshot. This includes
details needed to display owners and collaborators if their project-level user
records are later changed or removed.

## Input Validation

Unless explicitly identified as optional, user-entered text fields are
required and must contain at least one character. Project, Key Result, and
Initiative descriptions are optional and may be left blank. Project
descriptions are stored and displayed as project metadata. This rule is
field-specific so that other optional text fields can be identified without
making all text inputs mandatory. Generated values, fields with specified
defaults, and the collaborator list (which may be empty) do not require manual
input.

Non-mandatory fields do not use an asterisk to indicate that they are required.
Optional text fields are identified with the suffix `(optional)` in their
field definition and UI label.

Invalid required Objective, Key Result, Initiative, review, and planning inputs
must show a user-visible validation message and must not be saved or submitted
until they are valid.

---

# Cadence Rules

Cycle periods use year-month values only, with no stored day-level dates.
Monthly, quarterly, and yearly cadence represent durations of one, three, and
twelve consecutive calendar months respectively. A cycle starts in the month
in which its planned OKRs are submitted (for the first cycle) or in the month
immediately following the preceding cycle's end month (for later cycles).

The cadence selected during a cycle's planning determines that cycle's own
duration and end month. A later cadence change affects only the cycle currently
being planned and does not alter any preceding cycle. Local calendar month is
determined on the user's computer.

---

# Progress Calculation

All progress values use percentages from 0 to 100.

Progress is a neutral measure of the current value relative to its target. Do
not label calculated percentages as “Off track,” “At risk,” or “On track” or
use status colors to imply trajectory. Show the measured current and target
values as primary evidence; percentages are a compact supporting summary.
Confidence and time-based risk are not currently captured and must not be
inferred from calculated progress.

---

# User Label Colors

Every user in a project has a clearly distinguishable label color.

- Colors come from a palette of at least 12 visually distinct hues (for
  example red, orange, amber, green, teal, cyan, blue, indigo, purple, pink,
  brown, slate). Shades of one hue family do not count as different colors.
- Colors are assigned by the user's position in the project's user list, so
  two users never share a color while the number of users does not exceed
  the palette. Beyond the palette, additional distinct colors are generated so
  that colors remain unique.
- A user keeps the same color in every view (Current Cycle, Kanban, Review,
  History, User Management, and the team viewer).
- Users that exist only in a completed cycle's snapshot receive a color that
  does not collide with current users.
- Label text and background meet WCAG AA contrast.
- Keep owner labels visually distinct from neutral progress indicators.
- The assignment is derived for display only and requires no schema change.

## Number Target

Formula:

```text
(currentValue - startValue) / (targetValue - startValue) * 100
```

The result is capped between 0 and 100 and rounded to the nearest integer.
Targets of 0 or targets equal to the start value are invalid.

---

## Percentage Target

Formula:

```text
(currentValue - startValue) / (targetValue - startValue) * 100
```

The result is capped between 0 and 100 and rounded to the nearest integer.
The start, current, and target values are percentages from 0 to 100. A target
of 0 or a target equal to the start value is invalid.

---

## Yes / No

Rules:

```text
Starting value: No (fixed)
Current value: No or Yes (user-selected)
Target value: Yes (fixed)

No = 0%
Yes = 100%
```

The user selects the current value from a dropdown; the starting and target
values are displayed as fixed metric endpoints and are not editable.

---

Threshold and Milestones metric types are out of scope for the MVP. Empty
milestone lists are invalid if milestone support is added in a future version.

---

## Objective Progress

Formula:

```text
Average progress of all Key Results
```

Example:

```text
KR1 = 80%
KR2 = 60%
KR3 = 40%

Objective = 60%
```

Objective progress is rounded to the nearest integer. An Objective without a
Key Result is invalid and cannot be saved.

---

## Initiative Progress

Initiatives use a manually managed progress value.

Allowed range:

```text
0-100%
```

Additional rule:

```text
Status = done

=> Progress automatically becomes 100%
```

Progress is rounded to an integer. When changing a done Initiative to any other
status, the user must enter a new progress value below 100 before saving.

# Editor Navigation and Phase Guidance

The editor's primary navigation consists of **Current Cycle**, **Planning**,
and **Review**. Place **History**, **People**, and **Publishing** in a
secondary **Workspace** menu. Show the selected section clearly and avoid a
repeated page-level title when navigation already identifies the screen.
Keep phase tabs disabled when their required project state is unavailable.

Show one prominent next-action panel appropriate to the project lifecycle:

- Without an open project, offer **Create project** and **Open project**.
- With a planning draft and no active cycle, show **Continue planning** (or
  **Plan next cycle** after a completed cycle), a concise readiness checklist,
  and **Activate cycle** when all planning requirements are met.
- During an active cycle, make **Update Key Results** the primary action and
  provide **Review cycle**, explaining that submission completes and locks the
  cycle.
- When planning requirements are met, route the user to the read-only plan
  summary before activation; activating starts the cycle and makes the plan
  active.
- When Planning is selected during an active cycle, explain that next-cycle
  planning unlocks after review submission and provide **Go to Review**.

Keep save state visible in the editor chrome and explain when saving prevents
activation or review submission. Disable those actions until the project data
has saved successfully, and provide a way to retry a failed save.

# Application Views

The application contains the three primary views above and secondary
Workspace views.

---

## 1. Current Cycle

Purpose:

Execution and tracking of the currently active cycle. The cycle remains
editable until its review is submitted.

Display:

- Cycle priorities (the cycle-scoped Company Goals)
- Objectives
- Key Results
- Initiatives
- Display Objective and Key Result owners as colored labels. See "User Label
  Colors".
- Use a compact cycle header with dates, cadence, the next relevant milestone,
  and the detailed cycle timeline. Keep Cycle priorities visible beneath the
  cycle context.
- Place Objectives immediately after the cycle context and expand them by
  default. Keep Objective descriptions visible. Collapse Key Results by
  default, but show each one's Initiative count in its summary.
- Show each Key Result's measure, units, current value, target, and neutral
  completion percentage without requiring expansion.

The timeline and next relevant milestone derive from cycle dates and the
current local date. They do not change the month-granularity cycle storage or
cadence rules.

Organization:

```text
Cycle priorities (ordered by priority)
Objectives (linked to one or more Cycle priorities)
└── Key Results
    └── Initiatives
```

Objectives should be displayed once, with all linked Cycle priorities
identified, even when an Objective is linked to multiple priorities. The
Initiatives board supports combined Objective, Key Result, owner, and priority
filters, with Key Result choices scoped to the selected Objective. It shows
the matching count, provides a clear-filters action, preserves filters while
status changes, and explains filtered empty states. A board-level Add Initiative
action requires explicit Objective and Key Result selections. Cards keep their
title, status, owner, priority, target date, and parent OKR visible;
descriptions and task lists are under optional details. Initiative forms keep
title, parent, owner, priority, target date, status, and progress in their
core fields, with description, tasks, task synchronization, and optional
collaborators grouped under optional details.

Clicking an editable item should allow editing. Cycle priorities are managed
in Planning; Objectives, Key Results, and Initiatives are editable in the
active cycle.

## 2. Review

Purpose:

Review the currently active cycle. A review may be submitted at any point
during the cycle.

Display:

- Objective performance
- Key Result performance
- Overall cycle performance
- Present Objectives and Key Results using the same expandable hierarchy,
  owner labels, linked Company Goal indicators, and progress summaries as
  Current Cycle and History.

An optional cycle summary is the arithmetic mean of its Objective progress
values, rounded to the nearest integer, with each Objective contributing
equally. Present this only as an approximate summary, not as a grade, and keep
the explanation secondary to the measured Key Result outcomes.

Structured review questions:

What changed, and what helped us make progress?

What got in the way, or turned out differently than expected?

What did we learn that should shape the next cycle?

What needs to happen next, and who will take it forward?

Show the final Key Result current and target values with the review prompts,
not behind a separate collapsed hierarchy. Guide the owner through outcomes,
reflection, obstacles, lessons, and next-cycle actions. Before submission,
show a final results-and-responses summary. Explain that a low percentage is
not by itself a failure. If submitted before the cycle end month, clearly state
that submission closes the cycle immediately.

All four responses are required. Saving a review draft does not complete the
cycle. An explicit submission action marks the review complete, makes the
cycle's data immutable, and unlocks planning for the next cycle.

---

## 3. Planning

Purpose:

Prepare the next cycle.

Workflow:

1. **Cycle priorities:** Review and keep, revise, reorder, add, or remove the
   cycle-scoped Company Goals for the upcoming cycle (maximum three). Ask
   whether these priorities remain relevant. Changes do not alter prior
   cycles.
2. **Objectives and Key Results:** Record the planning focus, then define one
   or more Objectives linked to one or more Cycle priorities. Keep each
   Objective visually grouped with its Key Results and alignment. Every
   Objective needs at least one Key Result before it can be saved. Explain the
   distinction with concise examples: “Increase qualified customer adoption”
   is an Objective; “raise activation from 40% to 60%” is a Key Result; “run
   onboarding workshops” is an Initiative.
3. **Review and activate:** Show cadence with the resulting start and end
   months (quarterly by default; monthly and yearly available). Before
   activation, show a read-only summary of the complete plan and explain that
   activation starts the cycle and makes these OKRs active. Require at least
   one Cycle priority, Objective, and Key Result before activation. Initiatives
   remain optional.

Rules:

- Planning for a subsequent cycle is unavailable until the active cycle's
  review has been submitted.
- Before submission, the planned cycle must have at least one Company Goal,
  Objective, and Key Result. Each Objective must have at least one Key Result.
- Initiatives are optional during planning and can be added at any time while
  the cycle is active.
- The selected cadence affects the duration of this cycle only; completed
  cycles and the preceding cycle's duration remain unchanged.

---

## 4. History

Purpose:

Display historical performance.

Capabilities:

- Browse completed cycles
- View historical objectives
- View historical key results
- View historical initiatives
- View historical review inputs

The user should be able to navigate between cycles and inspect details.
Display completed cycle context, then the historical Objectives and Key
Results with current/target metrics visible, and the submitted review
responses and Initiatives as supporting detail. History is read-only and
resolves assigned people from the completed cycle's user snapshots so later
user changes or deletion do not alter past displays. Use the same outcome
hierarchy and user-label colors as Current Cycle.

---

## 5. User Management

Purpose:

Manage the people available for assignment in the project.

Capabilities:

- View all users and their active/inactive state.
- Create users and edit their details.
- Deactivate users so they cannot be newly assigned.
- Delete users who are not assigned to any planned or active cycle.

When deletion is requested for a user assigned to a planned or active cycle,
show an informative message explaining that the user must first be removed or
replaced in all such assignments. Do not delete the user or change any
assignments automatically. Completed-cycle user snapshots remain unchanged.

# Team Viewer and Publishing

The team views OKRs through a read-only snapshot generated by the editor.

## Viewer

- One self-contained HTML file (default name `okr-viewer.html`) that opens in a
  modern browser on Windows and macOS from SharePoint, GitHub Pages, or a
  local copy.
- Reuses the existing components in a read-only mode. Editing, creation,
  deletion, planning, review submission, and user-management controls are not
  present; there is no autosave and no API access.
- Views: Current Cycle (OKR view and Initiatives Kanban) and History
  including submitted review answers. Planning, review drafting, and User
  Management are excluded.
- Always shows the project name and "Snapshot from <date and time>", and a
  visible hint when the snapshot is older than 7 days.
- Keep the read-only label, snapshot date, and stale warning visible. Use the
  compact cycle context and outcomes-first hierarchy from Current Cycle:
  Objectives and Key Results appear before secondary context, with their
  measured current/target values visible.
- Validates the embedded data with the shared schemas and shows a clear message
  for invalid or unsupported `schemaVersion` instead of partial content.
- Makes no network requests and declares a restrictive Content-Security-Policy.

## Snapshot

- A derived copy of the saved project plus metadata (`snapshotVersion`,
  `schemaVersion`, `generatedAt`, project name). It never alters `project.json`.
- Embedded JSON is escaped so project text cannot break out of the script
  block.
- User emails, the planning draft, and unsubmitted review drafts are omitted
  from the snapshot.

## Publishing

- The editor stores a publish folder and file name in application settings,
  not in `project.json`.
- **Publish viewer** writes the file through a temporary file and replacement
  so the file name and team link stay stable and readers never see a partial
  file.
- Publishing is blocked with a visible message while there are unsaved changes
  or a save error, or when the folder is missing or not writable. The result is
  shown in the UI.
- The folder can be a OneDrive-synced SharePoint folder (OneDrive uploads the
  file) or a folder (for example `viewer/`) inside this repository's Git clone.
- For a Git work tree, **Publish and push** stages only the viewer file,
  commits with a generated message, and pushes using the system `git` and the
  user's existing credentials. No tokens are stored. It never force-pushes and
  shows the exact reason for any failure.
- Optional, off-by-default prompt when closing the editor with unpublished
  changes: Publish, Skip, or Cancel. Nothing is published silently.

## Access and privacy

- The snapshot contains the exported data in plain text; access control is the
  responsibility of the storage location (SharePoint permissions or a private
  repository).
- Readers of the repository can also read the source code; this is accepted.
  `project.json` must not be committed to the repository.
- Verify that GitHub Pages is not publicly reachable with a harmless test file
  before publishing real data.

# Autosave

The application should save project changes automatically.

Requirements:

- Save after a short inactivity delay.
- Show saving state.
- Show saved state.
- Show save failure state.
- Saving a review or planning draft does not submit the review or activate the
  planned cycle. Both lifecycle transitions require an explicit submission
  action.

Suggested save delay:

```text
500-1000 ms
```

---

# Error Handling

Requirements:

- Failed saves must be visible.
- Corrupted files should not silently overwrite data.
- Invalid project files should generate an error message.
- The application should fail safely whenever possible.
- A failed or interrupted save must not silently replace the last valid project
  file with incomplete or corrupted data.
- Project writes should be serialized and use a safe replacement strategy,
  preserving a recoverable prior version.

---

# Backwards Compatibility

Every project file contains:

```json
{
  "schemaVersion": 1
}
```

Future versions must support migration of older project data.

Requirements:

- Existing projects should remain loadable.
- Migrations should be explicit.
- Unknown newer versions must not be overwritten.
- Validate the complete project before saving migrated data.

# MVP Acceptance Criteria

The MVP is successful when:

- A user can create a project.
- A user can open an existing project.
- A user can manage users in the People view.
- The editor presents Current Cycle, Planning, and Review as primary navigation,
  with History, People, and Publishing under Workspace.
- The editor presents a lifecycle-appropriate next action, readiness summary,
  and clear save-state guidance for activation and review submission.
- Planning is a three-stage flow with visible readiness, quarterly as the
  default for new drafts, cycle-scoped priority wording, and a read-only plan
  summary before activation.
- Current Cycle and viewer prioritize Objective outcomes and visible Key
  Result measures over secondary cycle context.
- Calculated progress is shown neutrally and is not presented as a time-based
  risk or confidence judgment.
- Progress indicators use the red/amber/green completion bands and retain
  numeric percentages without trajectory labels.
- Current Cycle and the viewer keep cycle context and priorities visible,
  expand Objective descriptions by default, and collapse Key Results with
  visible Initiative counts.
- The filtered Initiatives board scopes Key Results to the selected Objective,
  shows matching counts, preserves filters during status changes, and requires
  explicit parent selection for board-level creation.
- Key Result and Initiative descriptions are optional; empty or omitted
  descriptions remain compatible with schema-version-1 project files.
- Partially completed forms warn before discarding input. After creating an
  Objective, Key Result, or Initiative, the new item is brought into view.
- The desktop attempts to reopen the last project, with clear recovery guidance
  if the remembered file is missing or unreadable.
- Review shows measured outcomes with reflection prompts, a final response
  summary, and explicit early-close behavior when submitted before cycle end.
- A user can manage up to three company goals.
- Company Goals are ordered by priority and can be linked to multiple
  Objectives.
- A user can create cycles.
- Cycles use whole calendar months; start and end months follow the
  submission, cadence, and consecutiveness rules.
- Each cycle requires at least one Company Goal, Objective, and Key Result
  before activation; Initiatives may be added throughout the active cycle.
- Users assigned in planned or active cycles cannot be deleted until removed
  or replaced in those assignments.
- A user can define objectives.
- A user can define key results.
- Number Target, Percentage Target, and Yes / No Key Results calculate
  progress automatically.
- A user can define initiatives.
- Objective progress automatically updates.
- Initiatives can be visualized as a Kanban board.
- Reviews can be completed and stored.
- Submitting a review locks that cycle and unlocks planning for its successor.
- Historical cycles can be displayed.
- All project data survives application restarts.
- All project data is stored in one readable local JSON project file.
- Only one project is displayed at a time.
- A packaged Windows editor runs from its application folder without a
  separately installed Node.js/npm, console, or separate browser.
- The editor can generate a single self-contained read-only viewer HTML file
  from the saved project.
- The viewer opens in a modern browser without installation, admin rights, a
  server, or a console, and shows no editing controls.
- The viewer shows the project name and snapshot date, and refuses invalid or
  unsupported data with a clear message.
- Publishing replaces the same file in the chosen folder, keeping the team
  link stable, and is blocked while there are unsaved changes or save errors.
- Publishing to a Git work tree commits and pushes only the viewer file and
  reports failures without force-pushing.
- The editor source and build configuration can be transferred to macOS later
  without changing business rules or the JSON project format.
- Every user has a distinct, clearly distinguishable label color that is the
  same in every view, including the team viewer.
- The logo is shown in the editor and viewer header, as the favicon, and as the
  Windows executable and window icon.
